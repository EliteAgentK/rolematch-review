# Staying up when a provider is down

Status: steps 1 to 5 implemented and rehearsed locally (2026-10-23); step 6 planned. A live copy of the hosted dev project itself is blocked (see step 3). Owner direction (2026-10-23): Supabase is where data is stored, not the platform's foundation, and RoleMatch must keep operating when Supabase is down; the long-term aim is RoleMatch's own PostgreSQL on South African servers.

## What RoleMatch uses Supabase for

| Part | Today, during a Supabase outage | Target |
|---|---|---|
| Sign-in | **Fixed (step 1):** people already signed in stay signed in until their token expires (Supabase's default, one hour). New sign-ins and token renewals wait for Supabase. | Sign-in software on our own servers (Supabase's open-source auth server or an equivalent), never home-written. |
| Database | **Built (step 3), rehearsed locally:** with a copy configured, RoleMatch switches to it within seconds, keeps showing everything, and pauses saving with a clear message. | Read-only mode from a live copy of the database on a server we control (steps 2 and 3); later that copy becomes the main database. |
| Private file storage | **Originals are viewable from our own encrypted copy (step 5)**, with each view journaled first. **Uploads are held (step 4):** accepted, encrypted on our server, shown as waiting, and processed when service returns. | Uploads accepted and held encrypted, processed when service returns (step 4); originals also kept, under the same retention and deletion rules, in storage we control (step 5). |

## Step 1: sign-in tokens checked on our own server (done)

Before: every request asked Supabase whether the sign-in token was valid (answer cached 30 seconds), so a Supabase sign-in outage signed everyone out within half a minute, and a hung Supabase call hung the request.

Now (`server/src/tokens.ts`, wired in `server/src/supabase.ts`):

* The token's signature is checked here with Supabase's **public** key (ES256), read from the project's published key list (`/auth/v1/.well-known/jwks.json`). Only Node's own crypto is used; no package was added.
* The key list is fetched at most once per 30 seconds, re-read after 10 minutes, and **kept when a re-read fails**, so an outage signs nobody out. A key withdrawn from the list stops working on the next re-read.
* Refused without asking Supabase: a bad signature, altered claims, an expired token (30 s clock allowance), another issuer, a service or public key used as a person's sign-in (`role` and `aud` must be `authenticated`), `alg: none` or any unexpected algorithm, and a key of the wrong type.
* Left to Supabase, as before: an old shared-secret (HS256) token or a key not yet seen. If Supabase is unreachable then, the request is refused, never let through.
* Calls to Supabase sign-in now give up after 5 seconds instead of hanging.

The trade-off, stated plainly: a token cannot be withdrawn before it expires by a sign-out or password change made *outside* RoleMatch. Sign-outs through RoleMatch are remembered until the token would have expired, on the server that handled them (a copied cookie stops working at once) and, since 2026-10-27, in the database for every other server, which re-checks a token at most every 30 seconds (`TOKEN_RECHECK_MS`; `server/test/several-servers.test.ts` runs two servers on one database). Organisation membership is checked in our own database on every request, so removing someone from an organisation takes effect immediately. One follow-up: the token lifetime can be shortened in the Supabase dashboard if one hour is judged too long.

**Session length** (2026-10-27). A sign-in lasts 8 hours, for everyone (owner, 16 Nov 2026: a working day; until then each organisation could set it, default 10 hours), counted from the sign-in time the sign-in service writes into the signed token (`amr`; it does not move when the token is refreshed, checked against the dev project). Every server checks it on every request; at the end the session is signed out everywhere and the API answers 401 `AUTH-005`. The website warns a few minutes before (the organisation's setting) and then asks for the password in a window over the same page, so unsaved typing is kept; a different person signing in gets a fresh page. Proven by `server/test/session-length.test.ts` and `e2e/session.spec.ts`. Unsaved typing is not kept if the page is reloaded or closed.

**Document reading in separate processes** (2026-10-27). `ROLE=api` servers only add jobs to the queue; `npm run worker` processes read them (`server/src/worker.ts`). If every worker stops, uploads still succeed and wait in a visible processing state; the first worker to start reads them. A worker that crashes mid-job stops checking in, and its job is put back in the queue within about 2 minutes (the handlers are safe to repeat). Before this, every server that started took back *all* running jobs, which would have restarted another live worker's work.

Proven by `server/test/tokens.test.ts` (seven cases, including forgery, misuse, key rotation and an outage) and `server/test/e2e.test.ts` (sign-out against the real dev project), and on 2026-10-23 with a real token from the dev project, checked locally and then during a simulated outage.

## Planned

2. **A test database on the development machine** (done 2026-10-23): `npm run test:local` runs all 370 tests against a local Supabase stack in about 2 minutes, against 10 to 15 on the hosted project, and does not depend on Supabase being up. Setup in `server/README.md`. It is also the first practice at running PostgreSQL ourselves, and the place step 3's copy will be rehearsed.
3. **A live copy and read-only mode** (built 2026-10-23). `READ_FALLBACK_DATABASE_URL` names a copy of the database. Every database call goes through one switch in `server/src/db.ts`. The main database is checked every `DB_CHECK_MS` (5 s): two failures switch reads to the copy, two successes switch back, and both switches are logged. The copy is opened read-only, so PostgreSQL itself refuses any save (error 25006), which the API returns as 503 `SVC-READONLY`: "Saving is paused… nothing has been lost." Every response in that state carries `x-rolematch-mode: read-only`, and the website shows a notice that appears and disappears by itself. The public health answer stays `{ok: true}`, revealing nothing. The rate limiter and the queue already fall back safely and pause rather than fail. Edits pause rather than queue, because a queued edit could silently clash with a change made elsewhere.

   **Rehearsed** with `npm run rehearse:outage` on the local stack. A second PostgreSQL subscribes to every change by logical replication; a CV is uploaded and published; the main database is stopped and later restarted. Measured 2026-10-23: the candidate reached the copy in 3 to 4 ms; RoleMatch switched to the copy 1.5 s after the main database stopped and returned 1.5 to 2 s after it came back; the recruiter stayed signed in and saw everything; a save was refused with the clear message; saving worked again; nothing was lost. Straight after the rehearsal all 370 tests pass. A cleanly stopped database is refused at once; a network fault that leaves connections hanging is detected more slowly (each check gives up after 3 s, so about 6 to 8 s).

   **For the hosted dev project: a copy refreshed every 5 minutes** (2026-10-23, owner's choice while a live copy is blocked, below). `npm run copy:watch` dumps the main database's public schema through the normal connection and restores it, in one transaction, into a local copy database (container `rolematch_devcopy`, port 54401, Colima). The main database is only read; if the dump fails the copy is left exactly as it was (seen on the first scheduled run, during a brief DNS failure). Supabase's user table (`auth.users`, password hashes) is deliberately not copied, so links to it are left out of the copy. The time each copy was taken is recorded, sent as `x-rolematch-copy-at`, and the website notice says "a copy from 12:02 (7 minutes old)", so a copy is never presented as live. First refresh: 28 s for the whole dev project, with every key table matching. Checked with real dev data: with its main database unreachable, RoleMatch started read-only, a recruiter signed in beforehand still saw a candidate added just before the copy, a save was refused with the clear message, and a new sign-in was refused with its own message.

   **Starting during an outage.** RoleMatch used to refuse to start if the main database was unreachable, because it first checks that the database structure matches the code. With a copy configured it now starts read-only from the copy. The structure check then runs before saving is allowed again, and in production a mismatch keeps it read-only rather than writing into a database that does not match. **New sign-ins wait** while saving is paused (503 `SVC-READONLY-SIGNIN`), because every sign-in is written to the audit log; people already signed in carry on.

   **Not yet possible against the hosted dev project.** Supabase's free plan allows a direct database connection, which replication needs, only over IPv6, and this Mac and its internet connection have none. The shared connection RoleMatch uses cannot carry replication. Options: Supabase's paid IPv4 add-on, an IPv6-capable connection, or a copy refreshed every few minutes instead of live (a dump through the shared connection). On our own servers (ADR-003) this does not arise, because we control the network. Logical replication copies rows, not table definitions, so a migration must be applied to the copy too (the rehearsal copies the definitions from the main database).
4. **Uploads held safely** (built 2026-10-23). While saving is paused, an upload passes the usual checks: size, genuine file type, and the organisation's limits, read from the copy. A file the copy already knows is answered as before. Otherwise the file and its details (including its name) are held on this server in `data/held`, each encrypted with AES-256-GCM under `LOCAL_ENCRYPTION_KEY`, written privately (owner only) and atomically. The response is 202 with stage `held`, and the website card says "Saved safely… processing starts by itself when the service is back; you do not need to upload it again", with no step shown as done. When saving resumes, and every minute after, held uploads are replayed through the same `storeUpload` path as a live upload, keeping the same document id. The audit entry records `held: true` and the time it was received, under the uploader's name and the original request id. Each is then deleted from the holding area. Limits: 50 waiting per organisation and 500 MB in all; beyond that, or with no key configured, an upload during an outage is refused with a clear message. A tampered held file fails its authentication tag and is left for a person, never processed. Proven by `test/held-uploads.test.ts` (encryption at rest, tampering, wrong or missing key, organisations kept apart, duplicates, limits) and by the rehearsal: a CV uploaded mid-outage was held, shown as waiting, then processed and published under the same id after recovery.
5. **Our own copy of original CVs** (built 2026-10-23). Each copy refresh also brings `data/originals-copy` in line with the documents: new originals are fetched (four at a time) and encrypted, and files whose document is gone are removed. A deletion therefore reaches this copy at the next refresh, and at once when the deletion job runs on this server. Files are named by a hash of the storage path, revealing no organisation or document. "View Original CV" uses the copy in two cases. If only Supabase's file storage fails, the view is audited as usual and the file comes from the copy. While saving is paused, the view is **journaled first**: written to `data/audit-journal`, durably (on disk before the file is sent) and encrypted. The journal is moved into `audit_events` with its original time when the database is back, and the journal entry's id becomes the audit row's id, so a repeat adds nothing. If the copy or the journal is unavailable the view is refused, never made unrecorded. Proven by `test/originals-and-journal.test.ts` and by the rehearsal: an original viewed mid-outage matched the uploaded file byte for byte, and its audit entry reached the log within 5 s of the real viewing time. The owner may prefer refusing original views during an outage altogether; that is a one-line change.

   All three stores (held uploads, copied originals, journal) share one module (`server/src/localVault.ts`: AES-256-GCM, owner-only files, atomic writes, fsync where it must be durable) and one key, `LOCAL_ENCRYPTION_KEY`.

   **Lessons from rehearsing this step**, kept for the production runbook. (1) After a database restart, the sign-in and storage services report healthy while their pooled connections are still dead, so readiness must be judged by real requests, not health checks. (2) An abandoned logical replication slot makes the main database keep its change log for ever, and the disk slowly fills, so production monitoring must alert on inactive slots. (3) The rate limiter counts sign-ups per address in the database, so repeated test runs from one machine use up the allowance; the local test tools clear those counts first (local database only).
6. **Alerts, an in-app banner and a status page hosted elsewhere**, so clients hear it from us first.

Then the self-hosting plan (two South African servers with automatic switch-over, tested backups, rehearsed recovery and costs) for the owner to decide on.
